LLD — object-oriented design

LLD tests something different from DSA: can you turn a fuzzy real-world requirement ("design a parking lot") into a clean, extensible class model in 45 minutes, using the right design pattern instead of the first one you remember? At staff/senior level, interviewers weight extensibility and SOLID discipline over cleverness — a design that survives three follow-up requirement changes beats one that's elegant but rigid. This page covers the foundations, the pattern catalog by priority tier, a drill set organized the way real loops sequence difficulty, and the free resources worth working through end to end.

Foundations

Before the patterns

Every LLD round starts by checking these are second nature — if they're not, no amount of pattern memorization will save the round.

OOP + SOLID

Prerequisite
•The four pillars (encapsulation, abstraction, inheritance, polymorphism) — full question bank on the Java + OOP page.
•SOLID as design pressure, not trivia: be ready to point at a specific class in your own design and say which principle it satisfies and why.
•Composition over inheritance — the default bias in almost every strong LLD answer.
•Interfaces as contracts: design to an interface first, then justify the concrete class.

UML you should be able to draw live

Communication
•Class diagrams — attributes, methods, visibility, and the four relationship arrows (association, aggregation, composition, inheritance).
•Sequence diagrams for the one or two critical flows (e.g. "what happens on checkout") — interviewers use these to check you've thought about interaction order, not just structure.
•State diagrams for anything with a lifecycle (order status, trip state, connection state).

Concurrency in LLD

Apple · Uber
•Thread-safe singletons, double-checked locking, and when enum is the cleaner singleton.
•Where to put the lock: guard the state, not the method — a common mid-interview correction.
•Producer-consumer, bounded queues, connection pools — see the concurrency question bank on the Java page for the primitives.

How the 45 minutes actually go

Format
1Clarify requirements and scope out loud (5 min) — nail down actors and core use cases before drawing anything.
2Identify core classes/entities and their relationships (10 min).
3Apply the design pattern that fits — justify it against at least one alternative (15 min).
4Code the critical path in working Java (10 min).
5Handle the interviewer's extension question without a redesign (5 min).

Pattern catalog

Design patterns by priority tier

Learn Tier 1 cold — draw the UML from memory. Tier 2 you should recognize instantly and be able to sketch. Tier 3 is "I know it exists and when it'd apply."

•Strategy — swap an algorithm at runtime (payment methods, sorting strategies, pricing rules).
•Observer — pub/sub between objects (notification systems, event listeners, stock tickers).
•Factory / Abstract Factory — decouple object creation from usage; abstract factory when you need families of related objects.
•State — behavior changes with internal state (order lifecycle, traffic light, connection state machine).
•Singleton, Builder (director + fluent builder for complex object construction), Decorator (dynamic behavior wrapping — pizza toppings, coffee add-ons), Adapter (bridging incompatible interfaces).
•Command (undo/redo, queued operations), Chain of Responsibility (approval chains, middleware pipelines), Template Method (algorithm skeleton with overridable steps).
•Composite (tree structures — file systems, org charts), Proxy (lazy loading, access control), Facade (simplified interface over a complex subsystem), Iterator (custom traversal without exposing internals).
•Flyweight (share expensive immutable state — glyph rendering, game particle systems), Prototype (clone instead of construct), Mediator (centralize object-to-object chatter), Visitor (add operations without touching the class hierarchy), Bridge (decouple abstraction from implementation), Memento (undo via saved snapshots).
